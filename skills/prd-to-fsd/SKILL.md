# PRD → FSD 转换 Skill

## 核心原则

1. **不猜**：接口路径、字段名、类名、方法名必须从实际工程代码中搜索确认
2. **不遗漏**：每个功能点都必须有对应的验收标准，每条验收标准必须可观测、可验证
3. **不模糊**：Then 禁止写"正常""正确""符合预期"，必须写具体页面表现、接口返回、数据结果
4. **不盲填**：PRD 已有的信息直接引用，不确定的即时交互确认，不臆造
5. **不脱离代码**：所有代码路径、类名、方法名、接口字段必须从项目实际工程代码中搜索确认
6. **不留疑问**：所有不确定事项和 PRD 与代码差异通过即时决策机制解决，最终交付的 FSD 无遗留项

## 输出路径规范

**正式交付物**：

```
docs/fsd/{需求简称}-fsd.md
```

例如：`docs/fsd/in91-电商平台件限制-fsd.md`

如果 `docs/fsd/` 目录不存在，先创建该目录。

**临时中间文件**（B 档访谈触发时生成）：

```
.tmp/prd-to-fsd/{需求简称}-prd-enriched.md
```

enriched PRD 是 AI 中间产物，仅供阶段二/三填充使用，**FSD 交付后由 4.3 节自动清理**，不放入正式 `docs/fsd/` 目录。

## 前置拦截：智能问询

在开始任何工作前，**先解析用户消息中已有的信息**，只对缺失的必填项使用 `question` 工具问询。

### 必填信息

| 项目 | 必填 | 自动提取策略 |
|------|------|-------------|
| **需求类型** | 是 | 从用户消息中识别"前端/后端/全栈"等关键词；无法判断时用 `question` 询问 |
| 主仓开发分支 | 是 | 从用户消息中提取 `feature/xxx`、`hotfix/xxx`、`release/xxx` 等分支名模式；写入顶层 `branch` 和主仓 `repositories[].branch` |
| PRD 文档路径 | 是 | 从用户消息中提取 `.md`、`.docx` 文件路径或链接 |
| 项目工程根目录 | 否 | 默认当前工作目录 `$PWD`；可从用户消息中提取 |
| 需求优先级 | 是 | 从 PRD 或用户输入提取 `高/中/低`；无法确认时用 `question` 询问 |
| 项目 ID | 是 | 从用户输入或已有项目配置提取；无法确认时用 `question` 询问，不用仓库名猜测 |
| 仓库清单与主仓 | 是 | 单仓自动读取 `origin` 仓库名并标记主仓；多仓时确认每个仓库、分支及唯一主仓 |

### 需求类型问询模板

无法从用户消息中识别需求类型时，强制使用 `question` 工具：

```json
{
  "questions": [
    {
      "question": "本次需求属于哪种类型？决定后续加载的 FSD 模板（前端模板/后端模板）",
      "header": "需求类型",
      "options": [
        {"label": "前端", "description": "APP/Web 页面、组件、交互逻辑、UI 自动化测试"},
        {"label": "后端", "description": "服务接口、数据层、定时任务、MQ、性能与容量"},
        {"label": "全栈", "description": "同时涉及前后端，将拆分为两次独立执行（先前端后后端，或反之）"}
      ]
    }
  ]
}
```

**全栈模式处理**：
1. 提示用户"全栈需求建议拆分为前端 FSD 和后端 FSD 分别生成。完成第一份后会提示是否继续生成另一份。"
2. 再用 `question` 让用户选择先做哪一份
3. 按所选类型执行完整流程，生成对应 FSD
4. 完成后用 `question` 询问"是否继续生成另一份 FSD？"
5. 用户确认后重新执行流程：
   - **PRD 路径不变，类型切换**
   - **检查第二份 FSD 的项目工程根目录是否与第一份一致**：一致则复用 git 环境；不一致则重新执行前置拦截的 git 切换流程（stash → checkout → pull → 探测目录）
   - 如果第二份 FSD 涉及不同仓库且不在当前工作区，询问用户是否跳过该仓库的代码探索

### 问询规则

1. 先解析用户消息，提取已有信息
2. 列出已提取和缺失的信息，只对缺失的必填项弹窗
3. 如果所有必填项都已提供，直接进入验证环节，不弹窗
4. **决策必须人工确认**：所有 `question` 工具调用等待用户实际响应，不引入超时默认，不替用户选择
5. 多仓库场景（PRD 提到多个独立服务）时，用 `question` 确认"本次 FSD 覆盖哪些仓库/子系统、每个仓库使用哪个分支、哪个是主仓"

### Git 仓库元数据规范

生成 YAML 摘要前必须读取 `references/repository-metadata.md`。仓库 ID 和分支均以实际 Git 命令结果为准；`project.id` 无可靠来源时必须询问用户。

### 问询模板（仅补问缺失项）

```
已从你的输入中提取到以下信息：

| 项目 | 状态 | 内容 |
|------|------|------|
| 需求类型 | ✅ 已识别 | 前端 |
| 开发分支 | ✅ 已提取 | feature/xxx |
| PRD 文档路径 | ✅ 已提取 | /path/to/prd.md |
| 项目工程根目录 | ✅ 默认 | $PWD |
| 需求优先级 | ✅ 已提取 | 中 |
| 项目 ID | ✅ 已提取 | sfxg |
| 仓库清单 | ✅ 已确认 | 主仓 repo-a@feature/xxx；协同仓 repo-b@release/xxx |

以下信息缺失，请补充：

{只列出缺失的必填项}
```

### 验证步骤

用户回答后（或确认无需补问后），**立即执行 git 环境切换**，使后续 PRD 读取、拒识检查、补全访谈、代码探索均在目标开发分支上进行：

1. **逐仓记录环境**：对 `repositories` 中每个本地仓库分别执行以下步骤，并记录仓库绝对路径、原分支、目标分支、stash hash：
   ```bash
   git remote get-url origin
   git branch --show-current
   git status --porcelain    # 先检查是否有未提交改动
   ```
   - 如果有改动：`git stash push -m "prd-to-fsd: auto-stash $(date +%s)"` 然后 `git rev-parse stash@{0}` 获取并记录 stash hash
   - 如果无改动：跳过 stash，不执行任何 stash 操作

2. **确认仓库 ID**：对每个仓库执行 `git remote get-url origin`，取 URL 最后一个路径段并去掉 `.git`；不得使用本地目录名覆盖可用的远程仓库 ID

3. **【中断保险】打印恢复指南**：在切换分支之前，在助手消息中**显式输出**一段固定格式的恢复指南，让用户可以截图或复制保存。这是用户主动中断（关闭终端、Ctrl+C、网络断开）时唯一可靠的恢复手段。

   ```
   ╔════════════════════════════════════════════════════════════╗
   ║  ⚠️  环境恢复指南（请保存，中途中断时使用）                ║
   ╠════════════════════════════════════════════════════════════╣
   ║  仓库恢复清单：                                             ║
   ║  {REPOSITORY_ID} | {PATH} | {ORIGINAL_BRANCH} | {STASH_HASH} ║
   ║                                                              ║
   ║  如本次执行中途异常退出，请手动恢复：                       ║
   ║  请进入每个仓库目录，按清单逐仓执行：                       ║
   ║    git checkout {ORIGINAL_BRANCH}                            ║
   ║    git stash apply {STASH_HASH}    # 仅在该仓有 stash 时     ║
   ╚════════════════════════════════════════════════════════════╝
   ```

4. **逐仓分支切换**：如果仓库当前已在 `repositories[].branch`，跳过 checkout；否则在对应仓库目录执行 `git checkout <目标分支>`

5. **逐仓拉取远程**（安全策略）：
   ```bash
   git fetch origin <目标分支>
   git log HEAD..origin/<目标分支> --oneline   # 查看远程领先的 commit
   ```
   - 如果远程有新的 commit，且当前工作区有未提交改动（已在步骤 1 stash），可直接 pull
   - 如果远程有新的 commit，且当前工作区无改动，告诉用户"远程有 {N} 个新 commit"，询问是否 pull
   - 如果远程无新 commit 或用户确认 pull：`git pull origin <目标分支>`

6. 读取 PRD 文档确认文件存在且可读

7. 进入阶段一开始工作流程

**环境恢复时机统一（4.2 节）**：以下任何路径都必须对恢复清单中的每个仓库执行 4.2 节的环境恢复（`git checkout <该仓原分支>` + `git stash apply <该仓 hash>`）：
- 阶段一 1.1.1 节命中硬拒识
- 阶段一 1.3 节访谈失败
- 阶段二/三/四正常完成后
- 任何中断或异常退出

## 工作流程

### 阶段一：PRD 输入分析与质量评估

> 本阶段执行时已完成 git 环境切换，所有 PRD 读取、拒识检查、补全访谈、代码搜索都在目标开发分支上进行。任何失败/拒识路径都必须走 4.2 节统一的环境恢复。

#### 1.0 探测项目结构

git 切换完成后立即探测主源码目录，供后续所有代码搜索（含访谈期间的代码辅助验证）使用：

```bash
ls -d src/ app/ Sources/ packages/ lib/ 2>/dev/null
```

按优先级识别主源码目录：`src/` > `app/` > `Sources/` > `packages/` > `lib/`。

**探测失败处理**：

如果以上目录都不存在，**不直接拒识**，按以下顺序处理：

1. 用 `question` 工具询问用户主源码目录路径：
   ```json
   {
     "questions": [
       {
         "question": "未探测到标准主源码目录（src/app/Sources/packages/lib 都不存在）。请指定本次代码探索的主源码目录",
         "header": "源码目录",
         "options": [
           {"label": "项目根目录（.）", "description": "代码直接在根目录下"},
           {"label": "自定义路径", "description": "手动输入相对路径"}
         ]
       }
     ]
   }
   ```
2. 用户选"自定义路径"时，在对话中追问具体路径，AI 用 `ls` 验证存在性
3. 验证通过后将该路径作为主源码目录
4. 用户拒绝指定或 3 次指定都不存在 → 走 1.1.1 节"项目目录无法定位主源码"硬拒识，走 4.2 节统一环境恢复后退出

#### 1.1 读取 PRD（格式自适应）

根据 PRD 文件格式选择读取方式：
- `.md`：使用 `read` 工具直接读取
- `.pdf`：使用 `read` 工具读取（内置 PDF 解析）
- `.docx`：使用 `read` 工具读取内容（如失败则告知用户手动提供 md 版本）
- `.txt`：使用 `read` 工具直接读取
- `.html`：使用 `webfetch` 工具读取

#### 1.1.1 前置硬拒识场景

读取后如命中以下场景之一，**走 4.2 节统一环境恢复后退出**，不进入补全访谈。

| 场景 | 判定规则 | 拒识原因 | 引导建议 |
|------|----------|----------|----------|
| PRD 文件不存在或读取失败 | read/webfetch 返回错误 | 物理无法处理 | 提供有效路径 |
| PRD 是图片/截图（无文本内容） | 文件扩展名是图片格式（jpg/png/gif/webp）；或 PDF/docx 解析后无任何文本 | 当前不支持 OCR | 转 md 文本后重提交 |
| PRD 包含多个独立需求 | PRD 中出现 ≥ 3 个不共享业务流程的功能模块（如"需求一/二/三"或多个独立的"功能 1/功能 2/功能 3"标题段） | 范围爆炸，FSD 无法聚焦 | 拆分为多个 PRD 分别生成 |
| 访谈补全失败 | 任一轮次重试 1 次后回答仍然无效（按 1.3 节判定） | 用户无法提供关键信息 | 建议先与产品对齐再回来 |
| 项目目录无法定位主源码 | 1.0 节探测失败且用户无法/拒绝指定主源码路径 | 无可探索的代码 | 确认是否在正确的项目根目录下执行 |

#### 1.2 PRD 信息完整性判定（两档制）

按以下客观判定规则检查 4 项必需信息：

| 检查项 | 判定规则（满足即视为存在） |
|--------|---------------------------|
| **需求名称** | PRD 中存在显式标题或"需求名称："字段，且文本长度 ≥ 4 字 |
| **功能描述** | PRD 中至少存在一段包含"动词 + 对象"结构的描述，如"校验子项"、"上传图片"、"展示列表"；总文本字符数 ≥ 50 |
| **接口/数据**（接口名或字段名至少一项） | PRD 中至少出现一项：URL 片段（含 `/`）、REST 动词（POST/GET/PUT/DELETE）、接口字样（含"接口"/"API"/"RPC"/"MQ"/"topic"等）、字段名（驼峰/下划线标识符 ≥ 3 个） |
| **验收标准** | PRD 中存在"验收"/"Given/When/Then"/"测试"/"通过条件"等关键词，且后接 ≥ 1 条具体描述 |

> 触发条件、边界场景属于可选项，缺失不阻塞，由阶段二代码探索补全。

**分档规则**：

| 档位 | 触发条件 | 处理方式 |
|------|----------|----------|
| **A 档·信息充足** | 4 项必需信息全部满足判定规则 | 跳过 1.3 访谈，进入 1.4 范围界定 |
| **B 档·访谈补全** | 任一必需信息不满足判定规则 | 进入 1.3 节补全访谈 |

#### 1.3 补全访谈（B 档触发）

**核心机制**：访谈采用"question 工具选方向 + 对话式追问详述 + 代码辅助实时验证"三步法。git 已切换到目标分支，AI 在访谈过程中可主动搜索代码辅助用户聚焦。

**触发规则**（按缺失项分别触发对应轮次，已满足的项跳过对应轮次）：

| 缺失项 | 触发轮次 |
|--------|----------|
| 需求名称 或 功能描述 缺失 | 轮次 1（业务定位） |
| 接口/数据 缺失 | 轮次 2（技术定位） |
| 验收标准 缺失 | 轮次 3（验收定位） |

##### 三步法详解（以轮次 2 技术定位为例）

**步骤 1：question 工具引导选择补充方向**

```json
{
  "questions": [
    {
      "question": "PRD 缺少技术信息。请选择你能提供的信息类型（至少 1 项），下一步将逐项收集详述",
      "header": "技术定位",
      "multiple": true,
      "options": [
        {"label": "接口名称或 URL", "description": "如 /recommendVas 或接口中文名"},
        {"label": "关键字段名", "description": "接口字段或数据字段，如 attribute3"},
        {"label": "代码模块/类名", "description": "如 AddServiceIN91"},
        {"label": "类似已有功能参考", "description": "本次改造可参考的现有功能"}
      ]
    }
  ]
}
```

**步骤 2：对话式追问详述**（标准化模板）

AI 在助手消息中按以下固定格式提问：

```
你选择了【{选项1}】【{选项2}】...，请按以下格式逐项补充（每行一项）：

1. {选项1}：____
2. {选项2}：____
...

请直接回复内容，每行一项。
```

用户在下一轮对话中回复，AI 按行解析每项的值。

**步骤 3：代码辅助实时验证**

AI 拿到步骤 2 的回答后**立即在代码中验证**（不再额外询问用户）：

| 用户提供的信息类型 | AI 验证动作 | 结果处理 |
|--------------------|------------|----------|
| 接口名称或 URL | `grep -r "{URL片段}" 主源码目录` | 找到：在对话中告知"已找到，位于 `path:line`"；找不到：追问"代码中未找到，是否为新接口？或可能是 YYY（最相近候选）？" |
| 关键字段名 | `grep -r "{字段名}" 主源码目录` | 同上 |
| 代码模块/类名 | `grep -r "class {类名}\|interface {类名}\|func {类名}\|@Service\|@RestController\|@Component"` | 找到：定位到文件，记录入口；找不到：追问"未找到类 XXX，是否为新建？请确认拼写" |
| 类似已有功能参考 | 按功能名搜索 | 找到：记录参考路径；找不到：追问"未找到 XXX，请提供更具体的功能名或文件路径" |

**多候选消解**：如果搜索找到 ≥ 2 个候选，立即用 `question` 让用户选择（不拖到阶段二）。

> **多候选 question 不计入访谈轮次**：步骤 3 触发的多候选选择 question 属于"代码验证子流程"，与访谈轮次（1/2/3）独立。同一轮次内同一 question 工具调用可承载多个选项的候选选择，避免重复弹窗。每轮访谈最多触发 1 次多候选 question。
>
> **候选数量超 5 的处理规则**：
> - **选择前 5 个的标准**（按优先级）：① 关键词出现次数最多 ② 文件最近修改时间最新 ③ 文件路径深度最浅（更接近主源码根目录）
> - **不提供"其他"选项**：避免绕过轮次限制陷入无限追问。如果用户认为前 5 个都不对，需明确告知"代码中可能不存在你描述的目标，请确认是否为新功能或调整描述"，本轮访谈按"种子词未确认"处理，可选择继续走全新功能分支或重试 1 次

##### 轮次 1 · 业务定位 选项

- 要解决的业务问题
- 用户/系统的核心动作
- 完成后的可观察变化
- **需求简称**（用于 FSD 文件命名，访谈成功后立即固定，作为后续所有文件命名依据）

**轮次 1 代码辅助**：业务描述确定后，AI 用业务关键词搜索代码，发现类似已有功能时在对话中提示"代码中已有相关实现 `path:line`，是否参考？"作为参考信息（不强制）。

##### 轮次 3 · 验收定位 选项

- 用户操作 X 后能看到 Y（正向）
- 接口返回 Z 时系统行为是 W（数据驱动）
- 在某场景下系统不做某事（反向/边界）
- 暂无明确验收点（基于功能描述+代码推导，需用户接受质量降级）

##### 回答无效判定规则（客观）

满足以下任一条件视为回答无效：

| 规则 | 客观判定 |
|------|----------|
| 空回复 | 回复内容字符数 = 0 |
| 推卸性词汇 | 回复内容匹配正则 `^(不知道\|不清楚\|随便\|你看着办\|无\|没有)$` |
| 非标识符短回复 | 回复内容字符数 < 10 且不匹配标识符正则 `[A-Za-z0-9/_]{3,}` |
| 仅复述选项 | 回复内容与 question 选项 label 完全一致，无附加内容 |
| 技术定位轮次后无种子词 | 步骤 3 代码辅助验证完成后，AI 提取的可搜索关键词数 < 1 |

##### 失败判定

- 任意一轮访谈中，步骤 2 的用户回答无效 → 允许重试 1 次（在对话中明确告知"你的回答缺少具体信息，请按格式补充：xxx"）
- 同一轮次重试 1 次后回答仍无效 → 触发 1.1.1 节"访谈补全失败"硬拒识，**走 4.2 节统一环境恢复后退出**

##### 访谈成功后处理

1. **立即固定需求简称**：访谈结果中的"需求简称"作为后续所有文件命名的唯一依据
2. **生成 enriched PRD 临时文件**：`.tmp/prd-to-fsd/{需求简称}-prd-enriched.md`
3. **按章节模板合并内容**：

```markdown
# {需求名称}

## 原始 PRD 内容
[原始 PRD]
{原始 PRD 全文}

## 访谈补充

### 轮次 1·业务定位 [访谈补充·轮次 1]
- 要解决的业务问题：{用户回答}
- 用户/系统的核心动作：{用户回答}
- 完成后的可观察变化：{用户回答}
- 需求简称：{用户回答}

### 轮次 2·技术定位 [访谈补充·轮次 2]
- 接口名称或 URL：{用户回答}（代码验证：✅ 找到 path:line / ❌ 新接口）
- 关键字段名：{用户回答}
- ...

### 轮次 3·验收定位 [访谈补充·轮次 3]
- {用户回答}
```

4. **后续阶段的输入源**：阶段二/三均以 enriched PRD 作为输入；阶段二的"PRD 差异"检查（2.3 节）也基于 enriched PRD
5. **FSD 交付完成后自动清理**：`rm -rf .tmp/prd-to-fsd/`（4.3 节执行）

#### 1.4 范围界定

根据 PRD 内容和涉及的子系统，确定本次 FSD 的覆盖范围：
- 单仓库场景：自动读取仓库 ID 和当前/目标分支，生成一项 `repositories`，并标记 `primary: true`
- 多仓库/微服务场景：用 `question` 让用户确认覆盖哪些子系统、每个仓库的分支和唯一主仓；每个子系统在对应仓库目录下独立执行 2.2 节搜索（使用 `bash` 工具的 `workdir` 参数切换到各仓库根目录），结果合并到一份 FSD 中
- 如果涉及不在当前工作区的仓库，询问用户是否跳过该子系统的代码探索（仅基于 PRD 描述填充）
- YAML 中 `project.repository` 必须等于唯一主仓的 `repositories[].id`；顶层 `branch` 必须等于该主仓的 `repositories[].branch`

#### 1.5 关键词汇总（用于阶段二）

汇总以下来源的关键词作为阶段二代码搜索的种子词：
- **A 档**：从 PRD 中提取类名/方法名、URL 常量、接口路径、业务关键词、字段名
- **B 档**：从 enriched PRD 中提取（包含 1.3 访谈步骤 3 已验证过的代码入口）

B 档场景下，1.3 步骤 3 已经在访谈期间完成了部分代码定位，阶段二只需基于已知入口做更深入的调用链追踪和关联模块扫描，无需重复种子词验证。

### 阶段二：代码库深度探索

**此阶段是 FSD 质量的核心保证。必须在目标开发分支上执行，所有探索结果均来源于实际代码。**

#### 2.1 搜索限流与降级策略

| 限制项 | 策略 |
|--------|------|
| 搜索范围 | 限定在阶段一探测到的主源码目录下 |
| 每轮搜索次数 | 每轮控制 ≤ 5 次 grep/glob 调用 |
| 搜索结果过多 | 结果 > 50 个文件时，只读取匹配度最高的前 10 个文件 |
| 搜索失败降级 | 3 次搜索无结果 → 告知用户"未找到 X，请确认关键词"，跳过该项继续 |

#### 2.2 代码搜索（按优先级执行）

**第一轮：精确匹配**
- 搜索 PRD 中明确提到的类名、方法名，确认文件路径和实际方法签名
- 搜索 URL 常量定义，确认接口路径
- 搜索接口请求/响应结构体定义，确认字段名、类型、枚举值

> **全新功能分支**：如果第一轮所有搜索均为空（PRD 中提到的类名/方法名/URL 常量在代码中都不存在），判定为**全新功能开发**。此时跳过后续三轮搜索，开发范围从 PRD 描述推导，接口文档基于 PRD 描述和项目命名规范推断，标注推断依据（如"基于 PRD 描述推断，字段名按项目 CamelCase 规范推导"）。YAML 摘要中 `is_new_feature` 设为 `true`。

**第二轮：业务关键词扩展**
- 搜索业务关键词，发现 PRD 中未提及的相关代码
- 搜索接口路径中的关键片段，确认是否有其他调用方

**第三轮：调用链追踪**
- 从第一轮确认的入口方法出发，追踪调用链：
  ```bash
  grep -r "import.*{ClassName}" --include="*.ts" --include="*.kt" --include="*.swift" --include="*.java" --include="*.py" --include="*.go" {srcDir}
  grep -r "{MethodName}" --include="*.ts" --include="*.kt" --include="*.swift" --include="*.java" --include="*.py" --include="*.go" {srcDir}
  ```
- 确认数据流转路径：前端模式为 接口返回 → 数据解析 → 业务处理 → UI 展示；后端模式为 接口请求 → 鉴权/校验 → 业务处理 → 数据读写 → 事件发布
- 检查是否有设计模式约束（策略模式、模板方法等），确认集中改造点

**第四轮：关联模块扫描**
- 检查是否有其他模块依赖同一套逻辑（如集收/散收公用策略类）
- 搜索类似场景的已有实现，作为参考

#### 2.3 即时决策机制

在代码探索过程中，**每发现一个差异或不确定点，先收集，不立即弹窗**。

**收集规则**：将所有待决策项暂存到内部列表，按以下分类：

| 分类 | 示例 | 决策策略 |
|------|------|----------|
| 代码一锤定音 | 字段名大小写不一致、类型差异 | AI 自主决定以代码为准，写入注意事项小节（前端 3.5 / 后端 3.6） |
| 需用户确认 | 多候选入口、PRD 遗漏逻辑、字段语义不一致 | 按类型分批提问 |

**分批提问规则**（适配 `question` 工具格式）：

- **同类型问题合并为一个 `question`**：如所有"字段名不一致"合并为一个 `multiple: true` 问题
- **不同类型问题分批次**：先问字段差异，再问入口选择，最后问遗漏逻辑
- **每批最多 1 个 question**：避免连续弹窗

**question 调用格式**（必须严格匹配工具参数结构）：

```json
{
  "questions": [
    {
      "question": "代码中有以下字段名与 PRD 描述不一致，请确认以哪个为准",
      "header": "字段差异",
      "multiple": true,
      "options": [
        {"label": "以代码 phoneNum 为准 (推荐)", "description": "PRD 写 phoneNumber，代码实际为 phoneNum；以代码为准可避免接口对接错误"},
        {"label": "以代码 vasItemList 为准 (推荐)", "description": "PRD 写 vasList，代码实际为 vasItemList；以代码为准可避免接口对接错误"}
      ]
    }
  ]
}
```

> 注意：`question` 参数是字符串，`header` ≤ 30 字符，`options` 每个选项的 `label` 1-5 词，`description` 说明差异内容 + 推荐理由。推荐选项 label 末尾标注 `(推荐)`。

**AI 自主决策项**（不询问用户，直接写入注意事项小节（前端 3.5 / 后端 3.6））：
- 字段名大小写不一致但含义相同
- 字段类型差异（`int` vs `string`）但代码已明确
- 代码中无实际影响的结构差异

#### 2.4 探索结果记录

所有探索结果和决策结果直接融入后续 FSD 填充。

## 交互原则

- **智能问询**：先解析用户消息已有信息，只补问缺失项
- **决策必须人工确认**：所有 `question` 工具调用必须等待用户实际响应，**禁止**引入超时默认、禁止 AI 替用户选择推荐项。每个决策点由人确认
- **分批提问**：同类型问题合并为一个 `question`，不同类型分批次，不逐个弹窗
- **AI 自主决策**：代码一锤定音的差异 AI 自主决定以代码为准，写入注意事项小节（前端 3.5 / 后端 3.6）
- **给出建议**：每个 question 提供推荐选项（标注"(推荐)"），但最终选择由用户做
- **环境安全**：stash 前检查 `git status --porcelain`，记录 stash hash，用 `apply` 恢复
- **降级不崩溃**：搜索失败、PRD 信息不足时告知用户，可降级继续，不中断流程
- **拒识不强撸**：命中 1.1.1 节硬拒识场景时直接拒绝并引导，不强行生成 FSD

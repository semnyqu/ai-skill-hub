# 需求开发入口

## 入口关键词

显式触发关键词为 **`需求开发`**。当用户以“需求开发”开头，或明确说“启动需求开发流程”“进入需求开发流程”时，进入本 Skill 并按下方规则判断阶段。

例如：

- `需求开发：我想给后台增加批量导出功能，目前只有一个初步想法。`
- `需求开发：请根据 @docs/PRD.md 生成 FSD。`
- `需求开发：FSD 已通过准入检查，请开始实施。`

除非用户明确要求完整流程，即使命中入口词，也只推进到当前请求授权的阶段；不得把“需求开发”误解为默认授权修改代码或部署文件。

## 目标

把用户的需求交给适合的下一项 Skill。先判断需求处于探索、规格编写、准入检查、计划或实施阶段；只调用当前阶段需要的 Skill，不重复跑完整流程。

## 知识库与代码联合分析策略

需求入口在路由后、产出设计或 FSD 前，必须先建立当前项目的证据上下文。目标是按需求涉及模块定向检索，而不是无差别读取整个仓库。

### 1. 确认项目根目录

- 优先使用当前工作目录，并通过项目标志识别根目录，例如 `.git`、`AGENTS.md`、`package.json`、`pyproject.toml`、`go.mod`、`pom.xml`、解决方案文件或仓库配置。
- 若用户指定了项目路径，按指定路径检查；若当前目录不是项目根目录，向上定位最近的项目根目录。
- 多仓库需求逐仓识别根目录，并记录每个需求模块归属哪个仓库。
- 不因读取需求文档而切换分支、拉取代码、修改文件或清理工作区。

### 2. 识别需求模块

从需求文本、PRD、页面/接口名、业务术语和用户指定范围提取候选模块，建立：

| 信息 | 记录内容 |
|---|---|
| 业务域 | 用户、订单、结算、权限等业务概念 |
| 系统模块 | 服务、子系统、前端应用或仓库名称 |
| 代码线索 | 页面、路由、API、领域对象、表、事件或配置名 |
| 置信度 | 高 / 中 / 低及判定依据 |

优先用仓库目录、模块清单、服务目录、路由和 API 定义交叉确认。若涉及多个模块，拆成模块清单及模块间调用关系，不要强行归到单一模块。若模块置信度低且会改变检索范围或方案，先向用户确认；否则把候选模块作为待验证假设继续。

### 3. 定位知识库

按以下优先级查找知识来源：

1. 用户明确提供的知识库路径、链接或文档。
2. 当前项目的入口说明：`AGENTS.md`、`README`、`docs/README`、目录索引、知识库索引文件。
3. 与已识别模块同目录或按项目约定存放的设计文档、架构文档、领域词汇表、接口契约、ADR、运行手册和历史需求。
4. 代码中的模块说明、注释、schema、API 定义、测试和示例。

只搜索与候选模块、需求术语和被影响接口有关的路径。先读索引/目录说明，再定向搜索；避免递归读取无关的大型目录、生成物、依赖目录、日志、密钥和用户数据。知识库路径不可读或约定不明确时，明确记录“未能定位/读取”，不得假设项目没有知识库。

### 4. 形成证据清单

对每个影响模块至少对照：

- 知识库中的业务规则、架构边界、术语和既有决策。
- 代码中的真实入口、调用链、数据结构、持久化、权限和错误处理。
- 相关测试、API/schema、配置及跨模块依赖。
- PRD/用户描述中的目标、范围和验收条件。

记录结论、来源路径/章节或代码符号、证据日期（若可得）及可信度。知识库描述意图和约束，当前代码证明现状；两者不一致时并列记录，不能静默选择一方，也不能把代码现状当成业务意图。影响功能行为、兼容性、安全、数据或模块边界的冲突必须向用户确认；低风险实现细节可提出带依据的建议。

### 5. 按阶段使用证据

- 想法模糊：把模块与知识库发现作为 brainstorming 的上下文，再澄清目标和决策；探索阶段不把旧设计直接当成用户确认的新需求。
- 已有 PRD：将 PRD、模块知识库证据和代码事实一起交给 `prd-to-fsd`；FSD 应区分需求要求、当前实现、决策和未决问题。
- FSD 准入：调用 `fsd-readiness-check` 检查规格完整性；该 Skill 不替代业务知识冲突确认。
- 实施：计划中列出模块、代码入口、相关知识文档、数据/API 影响和验证路径；编码阶段按测试及调试 Skills 执行。
- 交付：报告实际查阅的知识库与代码证据、未能读取的资料、采用的决策和剩余风险。

### 6. 知识库检索停止条件

满足以下条件即可停止扩展搜索并进入分析：已识别受影响模块；已找到可用模块索引/核心文档或明确记录其缺失；已定位主要代码入口和相关接口/数据结构；跨模块依赖已确认或标为待确认。若定向搜索仍无法建立这些证据，不要无限扫描，向用户说明缺口并询问最关键的知识库位置或模块归属。

## 路由判断

开始时检查以下信息：

1. 用户是否已有明确、可追踪的 PRD 或需求文档？
2. 用户目标、受影响对象、范围和成功标准是否足够明确？
3. 当前请求是在探索想法、生成开发规格、实施，还是排查问题？

按以下规则分流：

### A. 想法模糊或关键决策未定

满足任一条件时进入探索：用户只有一句想法；目标/用户/范围/成功标准存在关键歧义；用户仍在比较方案。

- 调用 `brainstorming`。
- 通过澄清形成设计方案并请用户确认。
- 设计确认后：若用户需要实施，调用 `writing-plans`；若设计需转成正式 PRD/FSD，先补齐 PRD，再进入 B。
- 不要仅因没有 PRD 就强行要求用户先写 PRD；简单事项可直接确定最小范围并继续。

### B. 已有 PRD，需形成开发规格

同时满足：有可读取的 PRD（文件或链接）且用户希望得到可交付的开发规格/FSD。

- 调用 `prd-to-fsd`，基于 PRD 和实际代码库生成 FSD。
- 如果 `prd-to-fsd` 在当前工具中不可用，说明缺失并给出手动选择；不可假装已经调用。
- FSD 完成后调用 `fsd-readiness-check`。
- `FAIL`：按检查项回到 FSD 补充，再重新检查。
- `PASS`：进入 C。

### C. 规格已确认，准备实施

输入是已确认设计或通过准入的 FSD，且用户要开始开发：

- 调用 `writing-plans` 制定分步实施计划。若用户要求立即实现且任务很小，可直接执行，不为流程额外造计划。
- 按计划调用 `executing-plans` 或逐项实施。
- 编写或修改代码时调用 `test-driven-development`，遵循项目测试约定。
- 遇到错误、测试失败或行为异常时，转用 `systematic-debugging` 定位原因；修复后回到实施流程。
- 完成后调用 `verification-before-completion` 核对交付与验证证据。

### D. 用户仅要求诊断现有故障

直接调用 `systematic-debugging`。确认修复后按需要实施变更，并在交付前调用 `verification-before-completion`。

## 重叠与跳过规则

- `brainstorming` 负责从不确定想法形成并确认设计；`prd-to-fsd` 负责将已有 PRD 工程化为 FSD。二者不可互相替代。
- `fsd-readiness-check` 只负责判断 FSD 是否达到开发准入条件，不负责生成 FSD。
- `writing-plans` 负责实施计划，不负责需求探索或 FSD 生成。
- `test-driven-development` 是编码阶段的方法；`systematic-debugging` 是问题出现时的排查方法；`verification-before-completion` 是交付前检查。
- 如果上游材料已经满足目标阶段要求，跳过已完成阶段，并说明依据。
- 发现入口信息不足但不影响路由时，先按合理默认继续；若关键信息会改变输出或造成不可逆决策，再向用户提出一个聚焦问题。

## 每次入口响应

先用简短说明给出：

1. 判定的阶段及依据。
2. 将调用的 Skill 和预期产物。
3. 是否存在缺失的 Skill、PRD、FSD 或准入结果。

随后执行当前可用的下一步，不要只复述流程图。
